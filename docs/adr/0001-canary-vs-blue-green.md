# ADR-0001: Canary для orders, Blue-Green для catalog

**Статус:** принято

## Контекст

Требование бизнеса — выкатывать изменения в рабочее время без простоя и без заметных пользователю ошибок. Rolling update из коробки Kubernetes не даёт ни контроля доли трафика на новой версии, ни быстрого отката: откат — это ещё один rolling update.

## Решение

| | orders | catalog |
|---|---|---|
| Характер | запись, деньги, внешние зависимости (БД, брокер) | только чтение, данные в памяти |
| Главный риск | ошибка в бизнес-логике проявляется на части запросов | регрессия видна сразу и на всех запросах |
| Стратегия | **Canary** 10 % → 50 % → 100 % с автоматическим анализом | **Blue-Green** со smoke-тестом и ручным переключением |
| Откат | автоматический, затрагивает ≤ 10 % трафика за ≤ 5 мин | мгновенный: смена селектора Service, старый цвет прогрет 30 мин |
| Стоимость | +2–4 пода на время релиза | ×2 ёмкости на время релиза |

### Почему ingress-nginx, а не Argo Rollouts / Flagger / Istio

- ingress-nginx уже стоит в кластере; `canary-weight` и `canary-by-header` закрывают задачу без нового контроллера в production.
- Логика анализа — 100 строк bash, покрытых тестами; её легко читать и отлаживать любому инженеру команды.
- Ограничение: canary возможен только для HTTP-трафика через ingress. Для межсервисного трафика (east-west) это не работает — при переходе на Service Mesh (Istio, в планах) стратегию стоит перенести на Flagger/Argo Rollouts.

## Последствия

- Миграции БД обязаны быть обратно совместимыми (expand/contract): во время canary старая и новая версии работают с одной схемой одновременно. Миграция выполняется Helm-хуком до старта canary.
- SLO-алерты считают только `track="stable"`: ошибки canary обрабатывает анализ в пайплайне, а не дежурный.
